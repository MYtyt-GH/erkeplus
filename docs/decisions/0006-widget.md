# 0006 桌面小组件：RemoteViews 自绘，只读缓存，数据变了主动推

- 状态：已采纳（规划阶段）
- 日期：2026-11-15

## 背景

用户希望把课表放到桌面。规划见 [docs/design/widget.md](../design/widget.md)。
三类做法摆得上台面：

1. **RemoteViews + XML 布局**：系统原生，任何桌面都能跑，但只能用 `LinearLayout`/`TextView`
   这一套，圆角、阴影、动效都受限；
2. **Glance（Compose for AppWidgets）**：写法与全项目一致，但要多引 `glance-appwidget`，
   多一层运行时与 R8 规则，`minSdk 26` 下还要处理它自己的兼容边界；
3. **自己画 Bitmap 塞进 `ImageView`**：想怎么画就怎么画，但文字缩放、深浅色、无障碍全部自己负责，
   而且改一个字就要重画整张图。

数据从哪来同样要定：小组件进程不可靠（见 [oem-compat.md](../design/oem-compat.md)），
在它里面发网络请求等于把「不确定什么时候能跑到」的执行环境当实时环境用。

## 决策

1. **RemoteViews + XML 布局自绘**。AndroidX 依赖保持现状，APK 只增加布局与少量代码；
   深浅色交给 `values` / `values-night` 资源，跟随系统，不用自己判断。
2. **只读本地缓存**（`TimetableCache`），小组件内不发任何网络请求。
   拿不到新鲜数据就明说「这周的课表还没下载」，给一键进课表页的路径。
3. **数据变了主动推**：课表缓存写入、外观设置改变时立刻 `updateAppWidget`；
   跨零点、改时间/时区/语言、放置、改尺寸、开机由系统广播或 `onUpdate` 触发；
   `updatePeriodMillis = 30 分钟` 只当兜底，不当主要机制。
4. **外观做成用户可选项**（卡片 / 毛玻璃 / 极简），默认卡片。壁纸千差万别，
   一种底色不可能同时讨好所有桌面，交给用户选比替用户猜好。
5. **地基按多组件设计**：抽象 `BaseWidgetProvider` + 共用刷新/深链/配色/尺寸换算，
   每个组件只写「纯模型 + 渲染 + Provider」。活动待办、活动看板将来照此接入。

## 理由

- 小组件的第一诉求是「稳定出现在桌面上、看得清」。Glance 的学习成本与体积收益不对等，
  而项目里没有第二处需要 Compose 之外的写法，多引一个 UI 框架等于多一个要跟版本的东西。
- 缓存已是「最近一次成功」的真相，且课表页每次刷新都会写它；让小组件读它，
  与「课表页离线也能看」是同一套逻辑，不需要为桌面单独维护一条数据通路。
- 主动推送比系统定时可靠得多：用户刚在课表页刷新过，桌面立刻跟上，
  这比「30 分钟后系统也许会跑一次」的用户感知强得多。

## 被排除的选项

| 选项 | 为什么不做 |
| --- | --- |
| Glance | 多一个 UI 框架依赖 + R8 规则，收益只是写法统一；小组件总共两类布局，不值 |
| Bitmap 自绘 | 文字缩放、深浅色、无障碍全要自己实现，改文案就得重画，维护成本最高 |
| 小组件里联网拉最新课表 | 后台执行时机不可控（OEM 会延迟/杀掉），失败还要自己兜，且与「凭据只在前台用」的边界冲突 |
| 依赖 `updatePeriodMillis` 定时刷新 | 系统下限 30 分钟且不保证准点，会把「准时」的错觉写进用户预期 |
| 每个组件一个配置页 | 入口太多；外观这类全局偏好放设置页一处即可 |
| 用 `ListView` + `RemoteViewsService` 做可滚动列表 | 桌面滚动体验与性能都不如固定行数 + 「还有 N 节」；本需求的课数很少 |

## 后果

- 需要在 `res/values` 与 `values-night` 各维护一份小组件配色（Compose 配色无法直接复用），
  改主题色时要两处一起改。
- 行数按「可用高度 ÷ 行高」动态算，必须配一组尺寸 × 字号的单测，否则小尺寸会被裁字。
- 周一早上可能出现「这周的课表还没下载」：先用「课表页刷新后预取下一周」缓解，
  整学期一次拉全是否可行**未验证**。
- `Chronometer` 能否在桌面持续走秒**未验证**；不生效就退化成静态钟点。
- 新增系统广播接收（日期/时间/时区/语言），不新增任何权限。
