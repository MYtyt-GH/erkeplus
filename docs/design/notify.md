# 我的阅办

官方 `#/needDealt` 叫「阅办」，一个页面装了两样东西：**待办**（要我去处理的事）与**消息**（系统发给我的通知）。
客户端就叫「我的阅办」，入口在「我的」页，排在「我的组织」之后、「我的附件」之前。

2026-11-15 与用户确认：待办那一半也做（管理员可能是未来的用户），所以不再叫「我的消息」——
只叫消息名不副实，官方这个名字用户也认得。

## 入口与层级

- 「我的」→「我的阅办」；调试入口 `am start ... --es probe notices`
- 层叠顺序（`MainActivity` 里按这个顺序写）：我的组织 ← **我的阅办** ← 活动详情 / 组织详情 / 网页壳。

  阅办写在「我的组织」之前，所以从消息里点「加入组织」落到我的组织后，返回回到的是阅办原来的位置，
  而不是一路退回「我的」。

## 版式

```
返回   我的阅办
[待办] [消息]
共 27 条
┌───────────────────────────────────────────┐
│ 10 条未读通知                全部标为已读 › │   ← 只在有未读时出现
└───────────────────────────────────────────┘
学时已发放                            今天 12:05
恭喜你参加的某活动，5.0 学时已发放
活动通知
───────────────────────────────────────────
```

- 两个 tab 用 FilterChip，和「我的组织」是同一套控件；默认停在**待办**，与官方一致
- 消息行：未读 = 标题加粗 + 左侧主题色圆点 + 正文用 `onSurface`；已读 = 常规字重、正文 `onSurfaceVariant`。
  只靠颜色深浅区分在暗色下不稳，所以字重和圆点一起上
- 时间：今天 / 昨天说「今天 14:20」，今年内 `11-15 14:20`，跨年只留 `2025-11-15`
- 标题用 `subTypeName`（「学时已发放」），一行，右边给时间；正文最多三行，超出省略
- 类型名 `typeName` 放最后一行小字：标题说的是「发生了什么」，类型说的是「这是哪类通知」
- 空态：待办「暂无待办内容」、消息「还没有消息」——都是正确状态，不写成报错
- 分页 10 条一页，滚到倒数第三条预加载下一页（听设置里的「预加载下一页」），末页不再发空请求
- 下拉刷新 = 重拉第一页 + 未读数

## 待办

- 一行 = 服务端给的 `{workDes, count, route}`；`icon` 给了才画（学生账号恒为空，真实取值没见过）
- `count > 0` 才有红角标
- 点一行：`route` 原样交给网页壳（`https://win.9xueqi.com/#/activityAudit/xxx`）。
  服务端给的是官方 H5 的路由，原生页对不上，所以**不猜、不假装跳转**；`route` 为空的行不可点
- 学生账号看到空列表，这是正确状态

## 点开一条消息落到哪

| 消息 | 落点 |
| --- | --- |
| `type=2` 且操作人不是我 | 活动详情 |
| `type=3` 且 `subType ∈ {13, 19}` | 「我的组织」 |
| `type=3` 其它 | 组织详情 |
| `type=2` 且操作人是我（管理员视角） | 没有对应页面 |
| `type=162` 黑名单 / 其它类型 | 官方路由没实测过，不猜 |

没有对应页面的那几类：**弹窗把正文给全**（列表里最多三行，弹窗不截断），同时标已读。

不做「打开官方页面」兜底：官方那条路由没有实测过，猜一个路径去打开等于把用户丢进 404。
用户真要看网页，走「更多 → 打开官方页面」。

## 已读

- 点开一条未读 → 立刻在本地变成已读样式，同时发 `notice/read`；请求失败只提示一句，样式不改回去
  （用户已经看过了，变回未读只会让人以为没点上）
- 「N 条未读通知」→ `notice/read-all {id: 0}`，成功后重拉第一页。**不弹二次确认**：
  官方也是点一下就生效，而且服务端没有「标为未读」，确认框只多一次点击
- 未读数以服务端为准；本地只在点开一条时减一

## 未读数与角标

- 未读数只在进这一页时拉一次；第一次切到「消息」tab 才拉
- 「我的」页**不加未读角标**：加了这个数就得为它单独轮询，而服务端没有推送通道
  （没有 WebSocket，H5 自己也不轮询，见 [规划](../plan/notifications.md)）
- 系统通知（WorkManager 轮询 + 通知渠道 + 开关）是下一阶段，不在这版

## 数据

`NotifyRepository`：`list` / `unreadCount` / `markRead` / `markAllRead` / `processing`。
字段与实测结论见 [接口记录](../api/win-9xueqi-api.md) 的「我的消息」一节。三个坑也在那里：
响应没有 `lastPage`（自己按 `pageNum * pageSize >= total` 算）、
`dynamic/unread/count` 返回字符串（消息这个不是）、`showDelete` 是字符串 `"false"`。

## 验证记录（2026-11-15，24090RA29C）

- **待办**：`activity/processing/list` 返回 `[]`，`statistics` 18 个计数全 0，页面显示「暂无待办内容」
- **消息**：真实账号 27 条，第 1/2/3 页 10/10/7 条；滚到底只发到第 3 页，第 4 页那次空请求没有发生
- **落点**：学时已发放 → 活动详情（`jumpInfo` 指的那个活动）；成功加入部落 → 我的组织（返回回到阅办原位）；
  黑名单通知 → 弹窗给全文
- **已读**（探针直接调仓库）：`notice/read {id}` 未读数 10 → 9；`notice/read-all {id: 0}` 9 → 0，
  列表 `isRead` 全部变 1，都是立刻生效
- **未读样式**：这个账号的消息在这次验证里被「全部已读」清空了，真机上再也造不出未读，
  所以未读/已读的差别是用 debug 的 `NoticePreviewActivity`（合成数据）在暗/亮两套主题下看的
- **亮色整页**：同一个预览页 `--ez full true` 借用当前登录态把正式页面按亮色主题铺开验证
